# Model deployment workflow

Purpose: Stage a local Qwen model on Google Drive and deploy it on Vast with a persistent volume.
Read when: Uploading a model, choosing a host, or recovering an interrupted deployment.

- Requires `rclone`, an authorized Google Drive remote, a Vast Google Drive connection, and an SSH key on the Vast account. The current Strata image supports its Qwen NVFP4 GPTQ format; place its files under `models/NAME/` with `pack/index.txt` directly below it, or pass an existing directory with `--source PATH`. A single GGUF file is also accepted for storage, but the current Strata image cannot run dense GGUF. The local `models/` directory and its private `.vast/` state are ignored by Git.
- `python vast.py model-upload NAME --remote gdrive_vast` copies to `gdrive_vast:models/NAME`, compares the local and remote contents, and stores a Google Drive MD5 manifest. Existing destination files are immutable; a conflicting file makes the upload fail. A model with existing workflow state is never overwritten.
- `python vast.py model-offers NAME --gpu RTX_5090 --hours 2` lists interruptible offers ranked by estimated rental and model ingress cost; `--region` defaults to EU. The cost assumes the advertised rate and omits retries. Record a machine ID from the table.
- `python vast.py model-prepare NAME MACHINE --size 150 --connection CONNECTION_ID` shows the storage and estimated ingress price, requires confirmation, creates only a standalone volume, and submits Cloud Copy from `/models/NAME` to `/qwen`. A volume is tied to its machine and incurs charges even without a GPU. After deleting it, `reset-volume NAME` checks that it is absent and clears its saved state. A second prepare is blocked if creation was successful or its outcome is unknown. If creation timed out, inspect `volume-list` and use `model-recover-volume NAME VOLUME_ID` to adopt only the matching label and machine.
- `python vast.py model-status NAME` displays the saved volume and the latest transfer log. The log can contain only a source inventory; it is not proof that copying finished. If a copy submission failed or timed out, check Vast first; `python vast.py model-copy NAME` explicitly confirms a retry and may incur duplicate transfer charges.
- Once the transfer is believed complete, find a current interruptible offer on the volume's machine and run `python vast.py model-launch NAME OFFER --bid USD_PER_HOUR`. The command asks whether to proceed despite unverified transfer completion and separately confirms the rental; it rents the GPU, waits for SSH, checks all files against the saved MD5 manifest, waits for the local API, and opens `127.0.0.1:8080` as an SSH tunnel. `--key`, `--port`, and `--timeout` are optional.
- GPU billing may begin before SSH, checksums, or model loading finish. If any post-rental step fails, the CLI reports the instance ID; the instance remains allocated and must be explicitly destroyed. Ctrl+C closes the tunnel, not the instance. Rerunning `model-launch` resumes a known existing instance, or asks before renting a new one if it was destroyed. For an unknown rental outcome, inspect the receipt and `vast.py list`; `model-recover-rent NAME` refuses to reset when a matching instance is visible. Use `model-recover-rent NAME --instance ID` to adopt an instance with the matching label and volume; either action requires confirmation.
- State contains the Cloud Copy log URL; treat `models/.vast/` as private and do not commit it. The user must keep this state and checksum manifest to resume. Repeated Cloud Copy and network usage can cost more than the estimate.
